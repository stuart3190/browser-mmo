## Correctness boundaries

- One pinned PostgreSQL session owns each assigned zone through advisory locks and writes its
  checkpoints. Duplicate hosts fail startup. Lost ownership or failed/ambiguous checkpoint writes
  fence simulation and publication, close sockets, and fail readiness. A replacement recovers
  only after acquiring the released lock. Startup failures release locks; migration/startup share
  a deployment lock. There is no clock-based lock stealing or automatic database failover.
- A versioned, game-data-bound recovery image and character health/position/cooldowns commit
  atomically before authoritative output. Enemy state, spawn/pickup identities, combat timers,
  lingering players and pending kills survive process loss. Unpublished predicted inputs may
  roll back. Synchronous WAL on the primary does not guarantee an asynchronous replica's RPO.
- A nonlethal enemy hit now emits local vitals every time. The browser also reconciles its health
  from authoritative damage messages. Existing death/respawn/regen/gear refresh paths remain.
- Production requires provisioned password authentication, disables dev auth, requires HTTPS
  origins and loopback services behind TLS ingress. Scrypt is memory/concurrency bounded;
  account/IP/work limits apply. Password rotation revokes sessions. No public signup/reset.
- Slow-client limits cover durable-output queues, socket buffers and direct error messages.
  Trusted forwarding is opt-in and loopback-only; ingress must overwrite client headers.
- Migration runners serialize and verify applied SQL checksums; pending migrations refuse live
  zone owners. Backup/restore uses a consistent snapshot, checksum/count manifest and economy
  integrity checks, refuses overwriting a nonempty target and revokes restored sessions.

The existing movement/controller/session/reconciliation/equipment hardening is retained.
See [operations](../deployment/PRE_ALPHA.md) for deployment and recovery procedures.

## Capacity: observations, not a hosting guarantee

Shared Linux VM: 12 virtual AMD EPYC 2 GHz CPUs, 48 GB RAM, Node 22.23.2, pnpm 10.28.0,
PostgreSQL 17.11 on loopback. Other tenants/services were present; no dedicated CPU/storage
reservation. Separate API, realtime, load-driver and PostgreSQL processes, no mock database.

`scripts/capacity.ts` opens real authenticated WebSockets, sends movement at 10 Hz, pings every
2 s, and performs authenticated inventory HTTP reads every 2 s per player. Players share the
village AOI. Full zone NPC simulation, checkpoint writes and session checks run normally.
Admission is staggered, using distinct simulated client IPs through trusted local ingress.
This is not a combat/boss/marketplace-mutation, connection-flood, WAN or long soak benchmark.

**No tested size maintained the 20 Hz target on this host.** Results are non-monotonic and do not

zero errors alone. Before external invitations, repeat on the intended host under combat/economy
traffic and sustained load; require the intended tick rate, bounded queues and acceptable tail
latency with explicit headroom. Diagnose storage/scheduler delay before introducing a broker or
rewriting the world. This deployment qualification remains external, not silently passed.

## Disposable backup/restore proof

The final script created isolated source and restore databases, migrated and seeded the source,
provisioned an account/session, created a character, granted an item and listed it in marketplace
escrow. Snapshot dump and fresh restore succeeded; all 18 table counts matched, including one
account, character, item, listing and session, two ledger entries and two history entries. Constraints,
wallet/ledger equality, escrow in both directions and nonnegative balances passed. Restored sessions
were revoked and a separate query asserted zero active sessions. A second restore into the occupied
target was rejected as expected. Both disposable databases were dropped in cleanup. No production
database was touched; no dump or credential is committed. [Sanitized proof](evidence/backup-restore.json).
